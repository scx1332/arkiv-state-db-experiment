# prekucki-v1: unpadded prefix-free keys vs main vs golem-db (2026-10-11)

Branch `experimental-prekucki-v1` (design: `docs/experimental-prekucki-v1.md`).
Machine `rogue-one`: AMD Ryzen 5 3600 (12 threads), NVMe RAID (`/dev/md0`),
64 GiB RAM; runs pinned to CPUs 2–9 with `taskset`; page cache dropped
before each run where `sudo -n` allows. The 5-minute load at run starts was
1.02–1.48 except one run at 3.95. Retained-state policy: engine defaults
(archive retention) for every arkiv run.

| Label | Revision |
| --- | --- |
| arkiv-old (main) | `187b349` (state layout 1: 164-byte padded term keys) |
| step 1 | `7518183` (variable-length trie, all key encodings unchanged) |
| arkiv-new | `d1d0c1a` (state layout 2; engine code identical to `371b079`/`80fd019`) |
| golem | golem-db `57c48ca` on MDBX |

Harness: golem-db-conformance-testing `686ddfc` with each arkiv revision's
own kit, built by `scripts/bench-compare.sh` (release, rustc 1.97.1 for the
harness, 1.90.0 for arkiv, redb 4.3.0). Ratios are of medians; **sig** means
the min..max ranges of three runs do not overlap.

## 2. Investigated: commit-growth and block-size/2

Both look slower above but overlap. Their individual runs are bimodal for
*both* revisions (commit-growth: ~1,700 or ~2,220 ops/s; block-size/2:
~3,000–3,200 or ~3,400–3,560), so a three-run median can land in different
modes. A seven-run recheck of only these two
(`results/20261011T130513Z-prekucki-v1-recheck`):

| scenario | arkiv-old runs | arkiv-new runs | median new/old |
|---|---|---|---|
| block-size/2-blocks-of-100 | 3031, 2997, 3043, 2842, 3071, 3042, 3421 | 3543, 3175, 3562, 3182, 3499, 3155, 3184 | 3,042 → 3,184: 1.05x (overlap) |

The direction reverses, and the step 1 run (section 3) put both at 1.00x and
1.04x. commit-growth is small-block, fsync-bound work in which term-key
length is a minor share; neither scenario shows a regression attributable to
the change. Neither is significant in either direction.

## 4. Sizes: encoded keys, reachable objects, proofs

`crates/arkiv-db-redb/examples/key_size_report.rs`, built unchanged against
`187b349` and against this branch; 20,000 records in blocks of 500 on a fresh
redb `DurableEngine`, each record with a 64-byte field. Sizes are
deterministic (identical in all three runs); write time is the median (min–max)
of three runs, measured outside the harness.

Logical key sizes (bytes, layout 1 → layout 2): term `color = "red"` 164 → 12;
`created = <u64>` 164 → 18; `title = <128-byte str>` 164 → 137; existence
term 164 → 4–8; record-key binding `rec/000000000001` 33 → 17. Under the
default limits no term key exceeds 164 bytes (`TermKey::max_len_for`).

- Reachable object bytes are the encoded trie objects the head reaches
  (rows, key bindings, terms, postings). Object *counts* are unchanged:
  Patricia compression already shared the padding, so shorter keys shrink
  leaf and extension paths, not the number of nodes. The saving is largest
  where term keys dominate (scalars: the 129-byte value padding disappears)
  and smallest for 128-byte strings (the value itself remains).
- The redb file size does not move: redb allocates in large regions, and the
  file also holds every retained historical version. The reachable-bytes
  column is the precise measure.
- Proofs shrink 2–5 %: the term path is a small part of an Eq proof, which is
  dominated by the posting set and row witnesses.
- In the deep-path rehash fixture (`tests/rehash.rs`), 200 record creations
  hash 510 nodes instead of 710 and stage 450 objects instead of 650: shorter
  keys put more nodes under the 32-byte inline threshold.

## 5. Regressions

None found. Scalar-only (index-layout/5, the `scalar` workload) and
maximum-length (`maxlen`) workloads were checked specifically: scalar-heavy
work is the largest gain (1.26x, −33 % object bytes, −13 % write time), and
128-byte strings are neutral (write time within run-to-run range, −1.8 %
bytes). The two scenarios with lower medians in the full run are noise
(section 2). The worst-case term key for the default limits is unchanged
(164 bytes), so proof walk bounds, reservations and proof-serving capacity
pre-checks are unchanged for default instances.
