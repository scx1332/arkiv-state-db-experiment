# Node soak from an empty state (2026-11-19)

The first long run of the [node soak](../node-soak.md): 7.5 hours of SDK
load against one producer that started from an empty genesis. It found
one defect, one number to measure and one question:

1. **Restart scales with chain length.** The node needed 614 s to come
   back at height 108,056. Before it listens, it rebuilds the JSON-RPC
   lookup index by reading and authenticating every block since genesis.
   The run itself failed on this: the harness gave the restart 10 minutes.
2. **`node.redb` is 71% free space.** The file is 146 GiB and holds
   41.5 GiB of data. 57.6 GiB is free pages redb never reused, and most of
   the file's growth during churn was this free space, not archived state.
   Once the file passed the page cache, reads went to disk and write
   throughput and read tails got worse. That part is expected.
3. **Inclusion latency doubles early in growth.** At about 150,000 entities
   transactions began taking two blocks instead of one, and the load
   generator's throughput halved with them.

No transaction was lost or reverted, blocks were produced every 250 ms
throughout, and the node's memory stayed between 250 and 360 MiB.

## Setup

- Machine: `rogue-one`, AMD Ryzen 5 3600 (12 threads), 62.7 GiB RAM, ext4
  on `/dev/md2`, kernel 7.0.0-22.
- Node: `arkiv-proposer producer`, release build of `6b68db9`, binary
  SHA-256 `dd24bbc590207854…`, 250 ms blocks, archive retention, default
  limits (`--read-concurrency 4`). Genesis: the smoke fixture plus one funded
  account.
- Harness: `scripts/soak/run.py --growth-min 240 --churn-min 180
  --readers-min 30 --drop-caches`; SDK `@arkiv-network/sdk` 1.0.1, Bun.
- Writes: `executeBatch` of 16 operations, 8 transactions in flight. Each
  batch of 8 waits for all 8 receipts before the next is sent.
- Results directory: `~/scx1332/soak-work/2026-11-19` on `rogue-one`
  (157 GB, kept), with the generated `report.md`.

390,853 transactions in all. Gas was 41,750 per create and 34,578 per
operation in the churn mix. Tx p50 is the median across 10-second windows.

## Growth: one block, then two

The first 5 minutes ran at the block cap: 512 creates/s with every
transaction included in the next block (p50 241 ms). From about 150,000
entities the p50 moved to about 490 ms. Each batch of 8 then took two
blocks, so throughput settled at exactly 256 creates/s, with about 5
transactions per block, a third of the 16-transaction cap. It stayed there
for the rest of growth, to 3.85 million entities.

The node had spare capacity: a state commit took 43–59 ms per 250 ms block
and the process used 60–78% of one core. The rate is set by inclusion
latency multiplied by the load generator's in-flight limit, not by a
saturated node. Why a transaction starts missing the next block at about
150,000 entities is **not yet explained**. Possibly admission (signature
recovery and the rent quote) or the block-assembly cut-off moves past the
point where the batch arrives. A soak with 32 transactions in flight would
show whether throughput rises.

State growth during growth was 9,476 allocated bytes of `node.redb` and
2,091 of `history.redb` per entity created. The 3-minute trial measured about
5,700 bytes per entity on a much smaller store.

## Churn: file growth, then reads from disk

Churn ran 11 creates, 3 patches, 1 delete and 1 extension per 16
operations, with a 10-minute lifetime, so the live set stayed at about
3.85 million entities plus about 100,000 churning ones.

| Minute | node.redb GiB | Commit ms/block | Created/s | Tx p95 ms (worst) |
| --- | --- | --- | --- | --- |
| 247 (start) | 35.0 | 59 | 227 | 525 |
| 285 | 46.0 | 88 | 150 | 3,008 |
| 342 | 71.6 | 98 | 140 | 4,487 |
| 380 | 79.6 | 108 | 109 | 4,254 |
| 418 | 110.6 | 118 | 100 | 5,340 |
| 456 (readers end) | 144.5 | 119 | 89 | 3,066 |

- `node.redb` grew 110 GiB over 2,398,720 churn operations, while
  `history.redb` grew only 4.7 GiB. Most of that growth is not data: see
  [Fragmentation](#fragmentation) below.
- The fastest growth, 110 to 145 GiB, came in the 30-minute readers phase,
  when 4 callers read continuously beside the writes.
- The file grew in bursts (36→48 GiB around minute 280, 50→72 GiB around
  minute 340). Both bursts coincide with throughput dips.
- Time in backend reads went from 46 ms per block early in churn to about
  300 ms per block from minute 340. That is when `node.redb` (72 GiB)
  passed the 60 GiB page cache. Commit time rose from 59 to 119 ms per
  block.
- Blocks were still on time: the slowdown appears as inclusion latency
  (up to 5.3 s at p95) and lower throughput, not as missed blocks.

## Fragmentation

redb's own statistics (`WriteTransaction::stats` and per-table
`stats()`), read from the stopped files after the run:

| File | Size | Stored | Metadata | Slack inside table pages | Free pages in the file |
| --- | --- | --- | --- | --- | --- |
| `node.redb` | 146.0 GiB | 40.4 GiB | 1.1 GiB | ~20 GiB | 57.6 GiB |
| `history.redb` | 14.0 GiB | 10.6 GiB | 0.01 GiB | 1.6 GiB | 1.8 GiB |

- Of the pages redb had allocated in `node.redb` (88.4 GiB), about 20 GiB
  is slack inside table pages, mostly the object table (15.9 GiB on
  31.0 GiB stored, 105 million objects of about 316 bytes). About two-thirds
  full is normal for a B-tree keyed by random hashes.
- That leaves about 27 GiB allocated but in no table: pages freed by
  recent commits and not yet released, or allocator state. This is not
  confirmed.
- The 57.6 GiB of free pages is the real waste. The file grew instead of
  reusing them. One possible cause, not tested: redb releases a page
  freed by a commit only once no older read transaction is open, and the
  readers phase, which grew fastest, kept reads open at all times.
- The `blocks` table of `node.redb` holds 9.1 GiB of block records (about
  84 KB per block, feed JSON included), beside the 10.6 GiB of bodies in
  `history.redb`.

Reading these statistics walks every page and took 23 minutes on the
146 GiB file, so the harness cannot sample them while the node runs.

## Reads

Probes of 100 sequential requests every 5 minutes. During growth every read
was flat: `getEntity` p50 0.4–0.5 ms, query p50 4–6 ms, p95 under 40 ms,
with no trend over 3.85 million entities. In churn the p50s barely moved
(5–18 ms), but the p95 of every query rose to 130–580 ms once the file
outgrew the cache. In the readers phase, 4 concurrent callers got 140
reads/s alongside writes, with 17 of 251,796 refused with ServerBusy
(0.01%).

One probe in churn failed on a ServerBusy refusal (`probe-failures.jsonl`).
The harness now counts refusals instead of failing.

## Restart

The harness sent SIGTERM at height 108,056; the node stopped in 0.06 s. The
harness then dropped the page cache and restarted it. After 10 minutes the
node had not opened its listeners, so the harness stopped the run, and
`report.md` shows no restart result.

Restarted by hand (page cache partly warm), the node was ready after
**614 s** at height 108,056, the height recorded at the stop. Profiling the
start (`perf`) showed one thread at 100%, almost all of it in Keccak and
secp256k1. `rpc::initial_state` (`crates/arkiv-node/src/signed/rpc/mod.rs`)
builds the transaction-hash and block-hash index by calling `shared_block`
for every height from 0. Each block is read from history and fully
authenticated, every transaction signature included. That is O(chain
length) on every start: about 5.7 ms per block here, or about 33 minutes per
day of 250 ms blocks (345,600 blocks). The index is also capped at 1,000,000 entries, and
the start ignores the capacity error, leaving later transactions unindexed.

The quick trials restarted in 5.6 s only because their chains had a few
hundred blocks.

## Follow-ups

- Persist the RPC lookup index, or build it after the node starts serving,
  and skip signature checks on blocks this node wrote itself. Restart time
  must not depend on chain length.
- Find why free pages in `node.redb` are not reused: compact a copy
  (`Database::compact`) to get its minimum size and the time it takes, and
  rerun growth and churn with and without concurrent readers.
- Check whether the `blocks` table needs the full feed record in the state
  file.
- Explain the move from one block to two at about 150,000 entities;
  rerun growth with `WAVE=32`.
- A state larger than the page cache reads from disk; that is normal
  operation, and the Sourcify soak will run that way from the start.
- The harness now allows `--ready-min` (default 60) for a start or restart.
